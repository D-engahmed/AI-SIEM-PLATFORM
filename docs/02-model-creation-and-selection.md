# 02 — Model creation and selection

Full process lives in `training/model_selection.ipynb` (generated by
`training/_build_notebook.py`, then executed with
`jupyter nbconvert --to notebook --execute --inplace` so it ships with real
output cells, not empty code). This doc narrates it for someone who won't run
it themselves.

## Candidates

Three model families, all on the spec's explicit allow-list (interpretable,
no deep learning, no unsupervised anomaly detection as the primary model):

- **XGBoost** — monotonic constraints on `fan_in_count`, `fan_in_rate_log1p`,
  `low_and_slow_ratio`, `ti_matched_positive`.
- **LightGBM** — same constraints, a second tree-based opinion with a
  different split-finding algorithm.
- **Logistic Regression** — interpretable linear baseline. If it got close to
  the tree models, that would be an argument for shipping the simpler model.

## Two-stage selection: tune each family, then compare the winners

For each family, a small curated hyperparameter grid (4 configs — not
exhaustive; this is 56k rows and 9 features, not a problem that needs 100
configs) is tried, each logged to MLflow as a nested run under a
`<family>_tuning` parent. **Selection uses the validation split; the test
split is touched exactly once, for the already-fixed winning config.**
Picking hyperparameters and reporting the winning number from the same split
is a well-known way to quietly overfit the split itself — this is why the
pipeline has three splits (70/15/15, time-ordered so the test split includes
the injected drift period), not two.

Current run's results:

| Family | Best config (by val AP) | Test AUC | Test AP | Test Brier |
|---|---|---|---|---|
| XGBoost | `max_depth=5, eta=0.1, subsample=0.7, colsample_bytree=0.7` | 0.898 | 0.880 | 0.134 |
| LightGBM | `max_depth=4, lr=0.1, num_leaves=15, feature_fraction=0.8` | 0.895 | 0.878 | 0.135 |
| Logistic Regression | `C=0.1` | 0.888 | **0.881** | 0.134 |

## Selection is NOT "highest AP wins"

Logistic regression has the highest raw test AP — and is disqualified anyway.
Decision order, most important first:

1. **Low-and-slow trap check** — non-negotiable. A candidate that fails this
   learned "rate" instead of "sustained volume", the opposite of what the
   spec asks for.
2. **Monotonicity compliance on `low_and_slow_ratio`** — also non-negotiable.
   XGBoost/LightGBM are compliant by construction (constraint enforced during
   training). Logistic regression is checked by coefficient sign — and
   **fails**: its fitted coefficient on `low_and_slow_ratio` is negative,
   violating the declared `+1` constraint. This isn't a data-generation
   accident; the notebook's own docstring predicted it: `low_and_slow_ratio`,
   `fan_in_count`, and `epoch_age_seconds_log1p` are all derived from the same
   two raw inputs, so an unconstrained linear model is free to push the "risk
   story" onto whichever correlated feature fits best — even if that gives
   one feature the wrong sign. Confirmed empirically, not assumed.
3. **`benign_shared_nat` false-positive rate** — the realistic failure mode
   most likely to page someone. Logistic regression is actually lowest here
   (0.063 vs XGBoost's 0.098) — a real point in its favor that the
   disqualification overrides for a documented reason, not silently.
4. **Test AUC/AP/Brier** — the tie-breaker among whatever survives 1–3, not
   the primary criterion.

**Current selection: XGBoost** (edges out LightGBM on val AP, 0.9043 vs
0.9031; both pass 1–2).

## Additional diagnostics run for every candidate

- ROC / precision-recall / calibration curves (section 6)
- **Permutation importance** — model-agnostic cross-check against gain-based
  importance, since gain can overstate features that get split on often even
  if the splits don't move predictions much. Computed by hand (shuffle one
  column, measure AP drop) since `sklearn.inspection.permutation_importance`
  expects a `.predict_proba(ndarray)` signature neither `xgb.Booster` nor
  `lgb.Booster` expose directly.
- **Partial dependence** — sweeps each monotonic-constrained feature across
  its full observed range (others held at median), confirming the constraint
  holds everywhere, not just at the two hand-picked probe points the trap
  check uses.
- SHAP summary plot for the tree candidate most likely to be selected.

## Registration

Winner is saved two ways (`src/config.py`'s `model_source`: `"file"` |
`"mlflow"`):

- `artifacts/model_latest.joblib` — fast path, no MLflow dependency at serving
  time. Now includes `model_family` (added 2026-08-18 — see "the bug this
  exposed" below).
- MLflow Model Registry (`correlation-ml-service-risk-model`, moved to
  `Staging`), tagged with `model_family` and `model_version` so
  `ModelScorer.load_from_mlflow` knows which flavor-specific loader to use
  without guessing.

Also saves `artifacts/feature_reference_distribution.npz` — the baseline
`src/monitoring.py`'s drift detection compares live traffic against (see
`docs/06-monitoring.md`).

## The bug this hyperparameter-tuning work exposed

`ModelScorer` used to build an `xgb.DMatrix` and call `.predict()`
unconditionally — correct only for XGBoost. That was invisible as long as the
notebook always happened to select XGBoost. Once tuning made the winner a
genuine, data-dependent outcome instead of a foregone conclusion, a LightGBM
win would have loaded fine (the joblib bundle format doesn't care) and thrown
on the very first real message in production. Fixed by storing `model_family`
in the bundle and dispatching `.score()` on it — see `src/ml_scorer.py`.

## A real operational gotcha, not swept under the rug

`training/train_model.py` — described in the notebook as "the lean script you
point CI at to retrain the already-selected model type" — currently **always
retrains XGBoost with one fixed config**, regardless of what the notebook
selected. Running it after the notebook **overwrites** the notebook's tuned
model with a simpler, untuned one at the same `artifacts/model_latest.joblib`
path. Not fixed here (would need `train_model.py` to read which family won and
retrain that specific tuned config, a real design decision about how "CI
retrain" should relate to "notebook selection" that wasn't asked for) — flagged
so it doesn't surprise anyone: **if you run `train_model.py` after the
notebook, re-run the notebook afterward if you want the tuned model back.**
